# AGENTS.md — правила для агентов ThodTalk

Этот файл обязателен для любого агента, который меняет код, собирает пакет или
публикует обновление. Подробная процедура выпуска: `docs/RELEASING.md`.

## Что важно знать

- Репозиторий: `ThodProd/ThodTalk`. Обновления приложение принимает **только** из
  его GitHub Releases по HTTPS.
- Приложение — Rust/egui для Windows x64. Сборка: `stable-x86_64-pc-windows-gnu`
  (Rust GNU + MinGW), CMake и `objdump` должны быть в `PATH`.
- Источники версии, которые обязаны совпадать:
  `Cargo.toml` → `[package] version`, `Cargo.lock` → пакет `thodtalk`,
  `hub/manifest.json` → `version`.
- Пользовательские данные лежат в `%LOCALAPPDATA%/ThodHUB/Data/thodtalk`
  (`THODHUB_DATA_DIR`). Обновление не имеет права их удалять или заменять.
- Не публикуйте секреты, ключи, токены, профили и содержимое `dist/`.
  `dist/`, `target/`, `test-data/`, `Release_v*` и `ThodTalk_v*.zip` — в `.gitignore`.

## Перед изменениями

1. Прочитайте `docs/RELEASING.md` и `docs/TESTING.md`.
2. Сохраняйте чужие незакоммиченные изменения. Не делайте `git reset --hard`,
   `git clean -fdx` и не удаляйте незнакомые файлы.
3. Для обновления кода не меняйте формат релизных файлов без обновления
   `src/updater.rs`, `scripts/package-release.ps1` и документации одновременно.

## Проверка изменений

```powershell
.\scripts\check.ps1          # cargo test + debug build
cargo test --locked          # быстрая проверка тестов
cargo build --release --locked
```

Сетевые тесты с публичными relay помечены `ignored` и требуют отдельного запуска;
не выдавайте их за пройденные, если не запускали.

## Выпуск обновления — кратко

Полная процедура и объяснение форматов: `docs/RELEASING.md`.

1. **Поднимите версию** (например, `0.3.11`):

   ```powershell
   .\scripts\bump-version.ps1 -Version 0.3.11
   ```

   Проверьте `git diff`: версия должна измениться в `Cargo.toml`, `Cargo.lock`
   и `hub/manifest.json`. Допишите изменения в `README.md`/release notes.

2. **Проверьте и закоммитьте**:

   ```powershell
   .\scripts\check.ps1
   git add -A
   git commit -m "chore: release 0.3.11"
   git push origin main
   ```

3. **Соберите, протестируйте и опубликуйте одной командой**:

   ```powershell
   .\scripts\release.ps1 -Notes "Что изменилось в 0.3.11"
   ```

   Скрипт требует чистую ветку `main`, запускает `cargo test --locked`, собирает
   ZIP, создаёт `thodtalk-release.json`, `thodhub-release.json`, `.sha256`,
   `verification.txt`, ставит тег `hub-v0.3.11` и публикует GitHub Release.

4. **Проверьте результат**:

   ```powershell
   gh release view hub-v0.3.11 -R ThodProd/ThodTalk
   ```

   В релизе обязательно должны быть:
   - `thodtalk-0.3.11-win-x64.zip`
   - `thodtalk-release.json`
   - `thodhub-release.json`
   - `thodtalk-0.3.11-win-x64.zip.sha256`
   - `verification.txt`

## Жёсткие правила выпуска

- **Не меняйте уже опубликованный релиз.** GitHub Release и его тег неизменяемы.
  Ошибка = новая версия (например, `0.3.12`), а не перезапись `0.3.11`.
- **Не публикуйте релиз из грязного дерева.** `release.ps1` сам это проверяет.
- **Тег только `hub-vX.Y.Z`** для стабильного выпуска. `vX.Y.Z` поддерживается
  кодом как запасной вариант, но для ThodHUB и старых версий используйте `hub-v`.
- **Не делайте prerelease/draft** для обычного обновления: приложение берёт только
  стабильные выпуски.
- **ZIP должен содержать** `manifest.json` в корне и `app/thodtalk.exe`; формат
  проверяет `src/updater.rs`. Не переупаковывайте ZIP после публикации.
- **SHA-256 и размер** в `thodtalk-release.json`/`thodhub-release.json` должны
  точно совпадать с ZIP. Иначе обновление будет отклонено.
- **Только официальный репозиторий.** Не добавляйте зеркала, сторонние URL,
  HTTP и редиректы в обновление.

## Как работает автообновление

- Приложение при запуске (через 3 секунды) и затем каждые 6 часов запускает
  `thodtalk.exe --update-worker`. Проверка не зависит от сохранённости профиля.
- Worker читает GitHub API, выбирает самый новый стабильный выпуск с версией
  больше текущей. Сначала берёт `thodtalk-release.json`, затем старый
  `thodhub-release.json`. Если описания нет — ищет ZIP и проверяет SHA-256 из
  `digest` GitHub или из `.sha256`.
- Скачанный ZIP проверяется по размеру и SHA-256, распаковывается с защитой от
  path traversal, симлинков и zip-бомб. Обязательно проверяется manifest.
- В интерфейсе появляется баннер «Доступно обновление X» в боковой панели.
  При включённой настройке «Устанавливать автоматически» приложение само
  перезапускается вне разговора (после 8 секунд простоя). Во время звонка
  обновление ждёт.
- Установка: helper ждёт завершения приложения, сохраняет старые файлы в
  `cache/updates`, заменяет `app/*` и `manifest.json`, при ошибке откатывается и
  запускает прежнюю версию. После успеха запускается новая версия.
- `THODHUB_API` означает, что приложением управляет ThodHUB: такая сборка не
  ставит обновление сама.

## Если релиз сломан

1. Не перезаписывайте тег и файлы.
2. Исправьте код, поднимите версию, повторите `release.ps1`.
3. Пользователи на сломанной версии получат следующую рабочую версию, если
   она больше по номеру и опубликована как стабильный `hub-v` релиз.
4. Локальные неудачные пакеты лежат в `dist/<version>/`; они не публикуются
   автоматически.

## CI

- `.github/workflows/ci.yml` — тесты и сборка на push/PR.
- `.github/workflows/release.yml` — ручная сборка и публикация по существующему
  тегу. Основной путь выпуска — локальный `scripts/release.ps1`; CI используйте,
  только если локальная сборка недоступна. Не запускайте оба способа для одной
  версии.
