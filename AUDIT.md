## Принятые требования

Новая Windows x64 программа на Rust, отдельное окно, клиент и запускаемый пользователем сервер в одном пакете. Тестирование выполняет агент. Голос, текст, группы и каналы для 10–15 друзей, русскоязычный интерфейс ThodHUB. Публикация запрещена приложенным заданием; работа локальная. Прямое требование Rust имеет приоритет над пунктами вложения про сохранение Bun/React/Electron.

Вложение требует остановиться после фазы 0 и показать план до изменения кода. Этот документ фиксирует результаты этой фазы. Готовой программы и проверенной сборки пока нет.

## Основные выводы

- apps/server/src/routers/messages/send-message.ts:147 обрабатывает HTML сообщения на сервере; :337 сохраняет content. apps/server/src/db/schema.ts:267 содержит текстовое поле content. Это не сквозное шифрование текста.
- apps/server/src/runtimes/voice.ts:578 создаёт WebRTC transport, :594 возвращает DTLS параметры. Это свидетельство транспортной защиты; самостоятельного подтверждения E2EE голоса в проверенных путях нет. Считать требование выполненным нельзя.
- apps/server/src/helpers/invites.ts создаёт по умолчанию 24-символьное приглашение и записывает его в activity log. Для нового приложения секреты приглашений не должны попадать в журнал.
- apps/desktop/src/main/deep-links/parse-deep-link.ts передаёт serverUrl, но не invite/channel отдельными полями результата.
- server.autoupdate уже false по умолчанию. Лишнего изменения не требуется.
- Короткий код не содержит достаточно информации для самостоятельного поиска произвольного сервера в интернете. Нужен каталог встречи или более длинное приглашение с адресом и проверкой ключа.
- Шесть символов не использовать как постоянный ключ шифрования. Для короткого подключения нужны краткий срок жизни, ограничения попыток, привязка к криптографической идентичности и подтверждение владельцем либо проверенный PAKE.
- Хостить сможет любой друг. Пока хост выключен, его сервер недоступен: независимость от конкретного владельца не означает работу без включённых узлов.

## Предлагаемая архитектура Rust

Нативное окно и клиент; сервер отдельным процессом того же поставляемого приложения. На клиенте ключи идентичности, расшифровка и аудио. Сервер хранит зашифрованные сообщения и пересылает пакеты, не получает групповые секреты. Локальный клиент владельца является обычным участником группы и может читать её сообщения.

Кандидат для группового протокола: OpenMLS (RFC 9420), с проверкой идентичностей, изменением ключей при смене состава, защитой от повторов и корректным сохранением состояния. Голос требует отдельного согласованного формата защищённых кадров и управления ключами; одного включения TLS недостаточно. Не разрабатывать собственные криптографические примитивы.

Кандидат для соединений: iroh, с отдельно проверяемой политикой discovery/relay. Публичная инфраструктура является внешней зависимостью, даже при шифровании. Для режима без внешних сервисов нужны LAN или доступный адрес собственного хоста; обещать соединение при любом NAT нельзя.

Ключи и история защищаются на диске; Windows DPAPI может защищать локальный секрет, но не заменяет E2EE и не защищает от вредоносного ПО в сессии пользователя. Все постоянные данные в THODHUB_DATA_DIR; временные данные отделены. Отдельно проектируется восстановление ключей и совместимость резервных копий.

Источники кандидатов: https://github.com/openmls/openmls/security ; https://blog.openmls.tech/ ; https://docs.iroh.computer/deployment/security-privacy . Выбор версий и API требует проверки при реализации.

## Десять основных рисков и проверок

1. Подмена ключей сервером: проверяемые идентичности участников и уведомление об изменении ключа.
2. Удалённый участник: ротация ключей и невозможность читать следующие сообщения/голос.
3. Повторы и изменение пакетов: проверка отклонения до выдачи содержимого.
4. Перебор приглашений: срок действия, квоты, отзыв и подтверждение подключения.
5. NAT/CGNAT: тест прямого пути и relay, ясная ошибка без доступного пути.
6. Аудио: выбор устройств, задержка, джиттер, потери, mute/deafen/PTT и переподключение.
7. Локальные данные: шифрование, DPAPI, аварийное завершение, восстановление без потери криптографического состояния.
8. Входные данные: лимиты размеров, безопасное декодирование аватарок, проверка ссылок и отсутствие выполнения команд из них.
9. Сервер: права на каналы, пределы памяти/очередей, защита от злоупотреблений, корректная остановка дочернего процесса.
10. Поставка: закреплённые зависимости, лицензии, отсутствие секретов, встроенные runtime и проверенный manifest/hash/size.

Шифрование содержимого не скрывает автоматически IP, время связи и объём трафика. Эти ограничения должны быть явно отражены в документации, а не обещаны как «полная безопасность».

## Фактически выполненные проверки

Git clone закреплённого тега успешен. Рабочее дерево исходника чистое. Прочитаны исходники и найденные выше пути. В PATH отсутствуют cargo/rustc и bun; стандартный C:/Users/Thod/.cargo/bin/cargo.exe отсутствует. D:/Every отсутствовал и создан для работы.

bun install, bun dev, функциональные тесты Sharkord и сборка Rust не запускались. С учётом выбора нового Rust-приложения установка Electron/Bun только ради запуска референса не выполнялась. Этот пункт исходного аудита остаётся непроверенным, а не пройденным. Rust toolchain и линковщик необходимо подготовить на этапе реализации.

На этапе проверки понадобятся два изолированных клиента и тестовый сервер с отдельными каталогами данных, тесты негативных криптографических сценариев и упаковки. Реальное двустороннее аудио и соединение между различными внешними сетями нельзя объявлять проверенными по локальному тесту.
